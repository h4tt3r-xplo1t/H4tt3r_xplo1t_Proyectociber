# recuperacion-asistida

## Objective
Issue #56 (A3b2a): administrator-assisted account recovery with a one-use reset code, and MFA reset of a privileged account approved by two distinct administrators (ADR 0004, decision 10; threat 46). Fold in the Gentle AI follow-ups of #51.

## Scope
- Allowed: `services/gateway/**`; `docs/BITACORA.md`, `docs/bitacora/**`; `docs/threat-model.md`, `docs/architecture/threat-model.json`; `odd/tasks/**`.
- Forbidden: `.claude/**`, `.github/**`, `docs/adr/**`, real secrets.
- Out of scope: anonymous help form (needs the E5 per-IP limit), break-glass (A3b2b), email recovery, per-IP rate limits.

## Design (from the issue and the code map)
- All auth, login, MFA and lockout logic lives in `services/gateway/src/gateway/auth.py`; admin routes in `admin.py` (`administrator_writer`, `_begin_change`, `_lock_target`, `_log_admin_event`, `busy_guard`).
- Reset code: `secrets.choice` over an alphanumeric alphabet, at least 16 characters; stored hashed with `hash_password` (Argon2id) in a new table (migration `0008`), one live code per user (issuing a new one voids the old), `expires_at = now + 15 min`, `used_at`; shown once with `NO_STORE`; an administrator cannot issue a code for their own account. Purge clause and key in `maintenance.py`.
- Anonymous reset route: same-origin and pre-session CSRF like login, listed in `PRE_SESSION` of the CSRF guard test. Generic 401 for any failure (unknown user, bad/expired/used code, missing or wrong second factor); failures counted on the login attempt key; locked account refused before slow work. Slow work (Argon2, transit) outside locks, final compare-and-set under the counter lock then the user row lock. Success: new password hash, code used, `invalidate_tokens` plus revoke every refresh family, counters reset, `password_reset_notice_at` set, security event.
- Login notice: new `users` column; shown in the next full-session login response and then cleared.
- MFA reset of a privileged account: request by one administrator, approval by a different one, neither the affected user; on approval clear the MFA columns and recovery codes, `mfa_enroll_until = now + ENROLL_WINDOW` (24 h), `invalidate_tokens`, revoke families, security events. Assumption (reversible): a pending request expires after 1 hour. Readers: see the open question.
- New routes follow the existing patterns: `NO_STORE`, fixed security events, `busy_guard` 503s, CSRF guard test cases.

## Acceptance criteria (issue #56)
1. The reset code expires after 15 minutes, is single-use, and issuing a new one voids the previous one.
2. A reset with an invalid, expired or used code answers the generic error and counts in the lockout.
3. An account with MFA or a privileged role cannot be reset without a valid second factor.
4. After a reset every session is revoked and the next login shows the notice.
5. One administrator alone cannot reset the MFA of a privileged account, nor an administrator their own.
6. New session routes require the sid-bound CSRF (covered by the guard test) and every action leaves a security event.
7. Observed RED per behavior change; pytest and ruff green locally and in CI; revisor-seguridad with no critical or high; threat model updated.

## Decisions
- 2026-10-15 (person): keep the strict rule for the reset code (second factor when MFA is active OR the role is privileged). A privileged account without MFA recovers by demotion to reader, code-only reset and re-assignment (pending until MFA enrollment); administrators by break-glass. Document this recovery procedure in T6.
- 2026-10-15 (person): a single administrator can reset the MFA of a reader (optional MFA), with the same mechanics minus the second approver; same accepted residual as the reset code of an account without MFA (ADR 0004, decision 10), logged and followed by the login notice. Privileged accounts keep the two-administrator rule. `docs/adr/**` is out of this issue's scope: record the decision in BITACORA and the threat model (T6) and propose an ADR 0004 update as a pending item.
